1 ReAct 与 Agent 架构

Q1 ReAct 是什么？你的项目怎么实现？
ReAct 就是让大模型先想再做。它先思考"我要干嘛"，然后决定调哪个工具，拿到结果后再思考下一步，这么循环下去直到给出答案。我项目里用 LangGraph 的 create_react_agent 实现的，工具调几次、调什么顺序都是 DeepSeek 自己决定的，不是我写死的。
Q2 为什么用 LangGraph 不用自己写 while 循环？
主要是它把 ReAct 的循环逻辑封装好了，我不用自己维护消息列表和退出条件。而且它原生支持流式输出，能实时把思考过程推给前端展示。自己写 while 循环要处理工具解析、异常、终止这些边界，容易出 bug。
Q3 怎么防止 Agent 死循环？
两层兜底。一是 LangGraph 自带 max_iterations 参数，超过次数强制停。二是我在 system prompt 里要求 Agent 最后必须输出一个 FINISH 行，我的 _parse_finish 函数会解析这个行判定结束。
Q4 Agent 怎么决定调哪个工具、传什么参数？
我每个工具用 @tool 装饰，LangChain 自动把函数名、参数、描述提取出来塞到给 LLM 的 prompt 里。LLM 看完决定调哪个，输出一个 JSON 包含工具名和参数，框架解析后执行对应函数，返回值再喂回 LLM。
Q5 和普通 pipeline 有什么区别？
pipeline 是写死的 search→write→push，if-else 顺序固定。我的项目里 Agent 搜几次、推不推、失败后重试还是回退，全看 LLM 当时的决策。同一段代码跑两次，工具调用顺序可能就不一样。这是 Agent 和脚本的本质区别。

2 容错与错误处理 ⭐ 面试重点

Q6 push_to_feishu 失败时 Agent 怎么处理？是硬编码重试吗？
不是硬编码重试。我把 push_to_feishu 设计成 agent 工具，失败时不抛异常，返回一个 "ERROR: HTTP 405" 这样的字符串。LLM 读到这个 ERROR 后自己思考，它可能想"重试一次"，再调一次又失败，它就再想"回退本地文件吧"。我用无效 webhook 实测过，Agent 真的走了 ERROR→重试→又 ERROR→回退这条链。
Q7 为什么失败返回字符串不抛异常？
这个很关键。抛异常的话程序直接中断了，LLM 拿不到 Observation 就没法做下一步决策。返回 ERROR 字符串，这个字符串会作为工具结果进入 LLM 下一轮的上下文，LLM 能读到具体错误是什么，从而决定重试还是换策略。这是让 LLM 具备"感知错误并改策略"能力的关键。
Q8 DeepSeek 挂了怎么办？
老实说目前 MVP 只接了 DeepSeek，没有 fallback。生产化我会加一个备用模型，比如 OpenAI 兼容的，在 _build_agent 里捕获连接异常后切换。另外 Tavily 搜索结果可以缓存，同关键词 1 小时内复用，减少外部依赖。这个我写在 README 的改进项里了。
Q9 所有渠道都失败，简报会丢吗？
不会。Agent 第一步一定先调 write_file 把简报写到本地 briefings 文件夹，然后才尝试推飞书。飞书失败回退后，本地文件已经存在了。DB 里也存了一份 markdown_content，前端能直接拉 DB 渲染。本地文件是兜底，不会丢。

3 安全约束

Q10 write_file 怎么防止 LLM 写恶意文件覆盖源码？
双重校验。第一层，路径必须以 briefings/ 开头，不然直接拒绝。第二层，把路径 resolve 成绝对路径后，用 Path.relative_to 判断它是不是还在 briefings 文件夹下面。这样就算 LLM 输出 "briefings/../app/main.py"，前缀过了，但 resolve 后跑出 briefings 子树，第二层就拦住了。
Q11 bash 工具怎么防危险命令？
我维护了一个正则黑名单，包含 rm -rf、curl、wget、sudo、shutdown 这些。LLM 调 bash 工具时先匹配，命中就返回 "ERROR: command not allowed" 不执行。另外 bash 是 agent 工具，只有 LLM 主动调才执行，不是用户直接输入，风险可控。
Q12 密钥怎么管理？有没有硬编码？
全走环境变量。config.py 用 os.getenv 读 DEEPSEEK_API_KEY 和 TAVILY_API_KEY。真实 key 存在 .env 文件里，这个文件被 gitignore 忽略不进仓库。仓库里只有 .env.example 模板，里面是空的。我扫过所有已追踪文件，没有真实 key 泄露。

4 SSE 流式与前端

Q13 为什么用 SSE 不用 WebSocket？
生成简报是单向的，服务端推事件给前端就行，前端不需要反向发消息。SSE 足够用，而且更轻量。WebSocket 是全双工，杀鸡用牛刀，还增加连接管理复杂度。
Q14 EventSource 只支持 GET，你生成简报是 POST，怎么解决？
EventSource 是浏览器原生 API，确实只支持 GET。但 SSE 协议本身支持 POST。所以我用 fetch 发 POST 请求，拿到 response.body 这个 ReadableStream，自己按 \n\n 分割事件，data: 开头的行 JSON.parse。这样既用了 SSE 格式又支持 POST 传 body。
Q15 stream_mode 重复消息 bug 是怎么发现和修复的？
第一次测试发现 tool_call_count 显示 109，明显不对。排查发现 langgraph 的 stream_mode='values' 每个 chunk 返回的是累积的完整消息列表，不是增量。我对每条消息都处理，历史消息被重复计入了。修复就是加了个 seen_ids 的 set，跟踪已处理消息的 id，只处理新增的。修完计数从 109 降到 10。
Q16 前端怎么展示思考过程？
用终端日志风格。深蓝黑背景配等宽字体，每行带图标——💡是思考、🔧是工具调用、✅是结果、🔴是报错。工具调用显示耗时，Observation 超长自动折叠。这样面试官一眼就能看出 ReAct 循环在转，"模型因为报错改变策略"的决策链也清晰可见。

5 数据存储与调度

Q17 SQLite 多线程写入怎么处理并发？
用 threading.Lock 串行化所有写操作，每次操作短连接用完即关。另外开了 PRAGMA journal_mode=WAL 提升并发读性能。因为 APScheduler 在后台线程跑定时任务，FastAPI 请求在主线程，两者都要写 DB，必须加锁。
Q18 定时任务怎么实现？为什么用 APScheduler 不用 Celery？
用 APScheduler 的 BackgroundScheduler，配 CronTrigger 从环境变量读 hour 和 minute，默认早上 8 点。在 FastAPI 的 lifespan startup 启动、shutdown 关闭。没用 Celery 是因为项目只有一个每日任务，Celery 要 Redis 中间件太重了。
Q19 怎么保证同一用户同一天不重复生成？
briefings 表有 UNIQUE(user_id, briefing_date) 约束。save_briefing 用 INSERT ... ON CONFLICT DO UPDATE 做 UPSERT，同一天重复生成会覆盖而不是插入新行。这样前端拉历史列表不会看到两条今天的。
Q20 简报内容存在哪？
双写。Agent 调 write_file 写到 briefings/YYYY-MM-DD.md 文件，这是本地兜底。同时 save_briefing 把 markdown_content 存 DB 的 briefings 表，前端直接从 DB 拉不用读文件。两个都有，文件防丢失，DB 方便查询。

6 测试与工程化

Q21 你的测试覆盖了什么？
41 个单元测试分两类。tools 测试覆盖安全约束——write_file 路径越狱用例、bash denylist 10 条危险命令、push_to_feishu 6 个分支全 mock 了 requests。agent 测试覆盖 _parse_finish 的 8 个分支、文件读取越狱拦截、概述提取和截断。都是纯函数测试不打真实网络。
Q22 Agent 端到端怎么测？
用真 LLM 跑，因为核心价值就是看 LLM 的自主决策行为，mock 出来没意义。但我会配无效 webhook 专门触发容错路径，验证 ERROR→重试→回退这条链是否走通。纯函数比如 _parse_finish 用单元测试，agent_log 决策链用 e2e 验证。
Q23 结构化日志怎么设计的？
JSON 格式单行输出，字段有 ts、level、logger、msg，extra 里带 agent_run、tool、duration_ms、status、tool_call_count、push_error 这些。生产方便 ELK 或 Loki 采集聚合错误。关键边界都打了日志——agent 跑完记 finish 带工具次数和推送状态，push 每个失败分支记 warning。
Q24 Dockerfile 怎么做的？
基础镜像是 python:3.10-slim。Dockerfile 分层缓存，先拷 requirements.txt 装依赖再拷代码，改代码不重装依赖。PYTHONUNBUFFERED=1 让日志实时输出。HEALTHCHECK 打 /health 接口。docker-compose 挂两个 volume——briefings 和 data 持久化简报和数据库，restart: unless-stopped 自动重启。

7 开放与设计问题

Q25 加新推送渠道怎么扩展？
当前每渠道一个 @tool。更好的设计是重构成 push_message(channel=...) 单工具多渠道，channel 可以是 feishu、dingtalk、email。密钥存 DB 不进 LLM 上下文，避免泄露。LLM 只学一个工具签名，prompt 里告诉它"该用户配了 feishu 和 email"，它自己决定推哪个。某渠道失败返回 ERROR，LLM 还能换渠道重试，比硬编码 if-else 灵活。
Q26 最大技术难点是什么？
两个。一是容错设计——让 LLM 通过 Observation 感知错误并自主决策重试或回退，关键是工具失败不能抛异常要返回 ERROR 字符串，这是和传统脚本最大的区别。二是流式数据去重——langgraph 的 stream_mode 返回累积消息，需要自己维护 seen_ids 去重，否则工具调用计数会爆炸式增长到 109。
Q27 项目有什么不足？
几个点。一是没有跨天新闻去重，同一新闻可能连续两天进简报，我会加 news_hash 字段让 LLM 避开已报链接。二是没有成本控制，用户狂点生成会烧 token，我会加配额和节流。三是 DeepSeek 单点无 fallback。这些我都主动写在 README 的改进项里了。
Q28 如果重做这个项目，你会改什么？
我会更早引入结构化日志和测试，而不是后期补。另外把推送渠道从一开始就设计成多渠道统一接口，而不是单工具。还有简报生成可以加缓存层，同一用户同一天重复生成直接返回缓存不重复调 LLM。
Q29 怎么验证容错真生效了？
我用无效 webhook 跑了端到端测试，然后看 DB 里 agent_log 字段的决策链。它会显示：调 push_to_feishu → 返回 ERROR HTTP 405 → LLM Thought "retry once" → 再调 push_to_feishu → 又 ERROR → LLM Thought "重试仍失败回退本地文件" → FINISH local only。这条完整链路在 DB 里存着，可以复现。
Q30 工具调用次数怎么统计？
在 _process_message 函数里，遇到 ToolMessage 类型就 +1，最后存到 DB 的 tool_call_count 字段。前端简报头部会显示"工具调用 N 次"。之前因为流式去重 bug 计数到 109，修复后正常在 8 到 12 次左右。

★ 实战示例：问题 → 定位 → 解决 → 思考

示例 1 · stream_mode 重复消息 bug（数字最有说服力）
问题：第一次端到端测试，tool_call_count 显示 109，明显不对，应该 10 左右。
定位：看 agent_log 有 256 条，发现 stream_mode='values' 每个 chunk 返回的是累积完整消息列表，历史消息被重复处理了。
解决：在 agent.py 加 seen_ids set，跟踪已处理消息 id，只处理新增的。修完计数降到 10。
思考：流式累积数据的常见陷阱。用 updates 模式能拿增量但丢状态，还是 values + 去重更稳。
示例 2 · push_to_feishu 容错（Agent vs 脚本的本质区别）
问题：飞书 webhook 可能无效或超时，直接抛异常 Agent 中断，简报就丢了。
定位：核心矛盾——LLM 怎么知道工具失败？只有拿到 Observation 才能决策。
解决：push_to_feishu 失败返回 ERROR 字符串（不抛异常），LLM 读到后自主决策重试或回退本地文件。
思考：抛异常是程序员思维，返回 ERROR 是 LLM 思维——让 LLM 能感知错误才有自主决策的基础。
示例 3 · write_file 路径越狱（双重校验防绕过）
问题：LLM 可能输出 ../../etc/passwd 或 app/main.py 覆盖源码。
定位：单一校验不够——前缀检查能被 briefings/../app/main.py 绕过。
解决：双重校验。第一层路径必须 briefings/ 开头；第二层 resolve 后 Path.relative_to 拦截 ../ 越狱。
思考：正则匹配路径不可靠，resolve 后比较绝对路径是标准做法。
示例 4 · 简报内容错误（最终输出 vs 实际产物）
问题：前端展示的简报是 LLM 收尾陈词（FINISH: local only...），不是真正的新闻。
定位：LLM 的 final_text 只是收尾，真正的简报是 write_file 写到本地文件的内容。
解决：finish 时检查 file_path，有值就读本地文件内容作为 markdown_content 存 DB。
思考：ReAct Agent 的特性——最终输出和实际产物可能分离，两者都要处理好。
示例 5 · SSE POST 限制（浏览器 API vs 协议本身）
问题：EventSource 只支持 GET，但生成简报要 POST 传 user_id。
定位：浏览器原生 API 限制，SSE 协议本身支持 POST。
解决：fetch POST + ReadableStream，按 \n\n 分割事件，data: 行 JSON.parse。
思考：备选 GET + query param 不优雅，WebSocket 没必要全双工，fetch + ReadableStream 最轻量。
